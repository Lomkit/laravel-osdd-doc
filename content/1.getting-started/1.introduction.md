Laravel OSDD (Open Source Driven Development) lets you split a Laravel application into **layers**: one Composer package per domain, living in your repository, with its own models, migrations, seeders, tests, routes and service provider.

## The problem

A fresh Laravel application keeps every domain in the same folders:

```
app/
  Models/User.php
  Models/Order.php
  Models/Invoice.php
  Http/Controllers/UserController.php
  Http/Controllers/OrderController.php
  Http/Controllers/InvoiceController.php
  ...
database/migrations/   ← every table of every domain
tests/Feature/         ← every test of every domain
```

Nothing separates billing from orders. Migrations, seeders and tests are global, any class can use any other one, and the dependencies between domains only exist in people's heads.

## The OSDD way

Each domain owns a package, and declares the packages it depends on:

```
functional/
  users/
    composer.json        ← "functional/users"
    src/Models/User.php
    database/migrations/
    tests/
  orders/
    composer.json        ← "functional/orders", requires "functional/users"
    src/Models/Order.php
    src/Providers/OrdersServiceProvider.php
    database/
    routes/
    tests/
technical/
  osdd/
    composer.json        ← "technical/osdd": the OSDD configuration
    config/osdd.php
```

- `functional/` holds the business domains: `users`, `orders`, `billing`.
- `technical/` holds the shared infrastructure: configuration, authentication wiring, observability.

The application stays one Laravel application: one `artisan`, one database, one deployment. The layers only change where the code lives and who may use it.

## How the pieces fit

| Piece | What it gives you | Read |
|-------|-------------------|------|
| **Layer** | A Composer package with `"type": "layer"`, installed through a local path repository | [Layers](/concepts/layers) |
| **Buckets** | The folders that hold the layers: `functional/` and `technical/` by default | [Buckets](/concepts/buckets) |
| **Boundaries** | `osdd:check` fails when a layer uses a layer it does not require, or when layers require each other | [Boundaries](/concepts/boundaries) |
| **Layer provider** | Each layer wires its own migrations, seeders, routes, views and config | [Service providers](/concepts/service-providers) |
| **Artisan twins** | `osdd:model`, `osdd:controller` and every other `make:*` twin write inside the layer you pick | [Generators](/commands/make-commands) |

## When to use Laravel OSDD

Laravel OSDD fits a Laravel application that holds several business domains in one codebase, one database and one deployment, often called a modular monolith. It suits a team that wants each domain to own its code and wants the dependencies between domains declared and checked.

It solves these problems:

- **No owner for a class or a table.** In a default Laravel application, every domain shares `app/`, `database/migrations/` and `tests/`. With Laravel OSDD, each domain is a layer that holds its own models, migrations, seeders, routes, config and tests.
- **Hidden dependencies between domains.** Each layer lists the layers it depends on in its `composer.json`. `osdd:check` fails when a layer uses a layer it does not require, or when layers require each other, and `--format=github` reports the violations on pull requests.
- **Tests and seeders that only run all together.** `osdd:phpunit` gives each layer its own PHPUnit test suite, and `osdd:seed --layer` runs the seeders of some layers only.

Laravel OSDD is not the right tool when:

- The application has a single domain. Laravel OSDD adds a `composer.json` and a service provider per layer, which brings little to a small application.
- The domains must be deployed or scaled on their own. Laravel OSDD keeps one Laravel application: it does not split it into services.
- The application runs Laravel 12 or older. Laravel OSDD 3.x needs Laravel 13. Laravel 12 applications stay on Laravel OSDD 2.x.

### Requirements

Laravel OSDD 3.x needs PHP 8.3 or higher, Laravel 13 and the `dom` PHP extension. A fresh project converts with `osdd:start`. An existing application keeps `app/` and moves domains into layers one at a time: see [Existing application](/getting-started/existing-application).

### Compared with other approaches

- **The default `app/` folder.** Laravel's default structure keeps almost every class in `app/`, grouped by kind (`Http`, `Models`, `Providers`), with migrations in `database/` and tests in `tests/`. Laravel OSDD groups the code by domain instead, and an existing application can keep `app/` next to its layers.
- **nwidart/laravel-modules.** This package stores modules in a top-level `Modules/` directory, each with a `module.json`, registers each module's service provider, and provides `module:*` commands such as `module:make` and `module:enable`. A Laravel OSDD layer is a plain Composer package with `"type": "layer"` and no `module.json`.
- **internachi/modular.** This package keeps each module in `app-modules/` as a Composer package installed through a path repository, and adds a `--module` option to Laravel's `make:*` commands. Laravel OSDD layers use the same Composer mechanism. Laravel OSDD sorts them into `functional/` and `technical/` buckets, generates code with `osdd:*` twins of the `make:*` commands, and checks the requirements between layers with `osdd:check`.
