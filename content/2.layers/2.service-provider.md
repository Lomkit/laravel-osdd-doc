title: Service Provider
description: Wire a layer's migrations, seeders, routes, views, policies and commands into the application.
---

Every layer has a service provider. It extends `Lomkit\Osdd\LayerServiceProvider` instead of Laravel's `ServiceProvider`, which adds these methods:

| Method | Use |
|--------|-----|
| `loadSeeders()` | Register the layer's seeders for [`osdd:seed`](/commands/osdd-seed) and `LayersSeeder` |
| `overrideConfigFrom()` | Override the config of any package with a layer file, see [Configuration](/layers/configuration) |
| `withRouting()` | Mount the layer's route files, see [Routing](/layers/routing) |
| `withViews()`, `withTranslations()`, `withComponents()` | Register views, translations and Blade components under the layer name, see [Views and components](/layers/views-and-components) |
| `withLivewire()` | Register the layer's Livewire components, see [Livewire](/integrations/livewire) |

`osdd:layer` generates this provider with the `provider` generator:

```php [functional/orders/src/Providers/OrdersServiceProvider.php]
<?php

namespace Functional\Orders\Providers;

use Lomkit\Osdd\LayerServiceProvider;

class OrdersServiceProvider extends LayerServiceProvider
{
    public function boot(): void
    {
        if ($this->app->runningInConsole()) {
            $this->loadMigrationsFrom(__DIR__ . '/../../database/migrations');
        }

        $this->withRouting(
            web: __DIR__ . '/../../routes/web.php',
            api: __DIR__ . '/../../routes/api.php',
            commands: __DIR__ . '/../../routes/console.php',
            channels: __DIR__ . '/../../routes/channels.php',
        );

        $this->withViews(__DIR__ . '/../../resources/views');
        $this->withTranslations(__DIR__ . '/../../lang');
    }

    public function register(): void
    {
        //
    }
}
```

Missing route files, views and `lang` folders are skipped, so every call is safe in a fresh layer. The generated provider registers no seeder: the `seeder` generator, or `osdd:seeder`, adds the `loadSeeders()` call.

## Registering the provider

Laravel boots the provider because the layer's `composer.json` lists it:

```json [functional/orders/composer.json]
"extra": {
    "laravel": {
        "providers": [
            "Functional\\Orders\\Providers\\OrdersServiceProvider"
        ]
    }
}
```

`osdd:layer` and `osdd:provider` add this entry for you. Run `composer update functional/orders` once after adding a provider so Laravel rebuilds its package manifest. Do not list layer providers in `bootstrap/providers.php`.

## Generators keep it in sync

Several generators add the line their file needs to the layer provider, so the new file is loaded without editing anything:

| Command | Adds to the provider |
|---------|----------------------|
| `osdd:migration`, `osdd:*-table` | `$this->loadMigrationsFrom(...)` in `boot()` |
| `osdd:seeder` | `$this->loadSeeders([...])` in `boot()` |
| `osdd:config` | `$this->overrideConfigFrom(...)` in `register()` |
| `osdd:command` | `$this->commands([...])` in `boot()` |
| `osdd:view` | `$this->withViews(...)` in `boot()` |
| `osdd:component` | `$this->withViews(...)` and `$this->withComponents(...)` in `boot()` |
| `osdd:livewire` | `$this->withLivewire()` in `boot()` |

A call the provider already makes is never added twice, whatever its layout. When the layer has no provider, or the method is missing, the generator prints the line to add by hand. See [Generators](/commands/make-commands#generators-that-wire-the-provider).

## Migrations

`loadMigrationsFrom()` comes from Laravel. It adds the layer's migrations to `php artisan migrate`:

```php
$this->loadMigrationsFrom(__DIR__ . '/../../database/migrations');
```

## Seeders

`loadSeeders()` registers seeders for [`osdd:seed`](/commands/osdd-seed) and `LayersSeeder`. Lower priorities run first:

```php
$this->loadSeeders([OrdersSeeder::class, OrderStatusesSeeder::class]);

$this->loadSeeders([RolesSeeder::class], priority: -10);
```

`osdd:seeder` adds this call when it creates a seeder. A seeder you write by hand needs it too.

## Configuration

`overrideConfigFrom()` merges a layer's config file over a key that is already loaded. The layer's values win. Call it from `register()`, see [Configuration](/layers/configuration).

## Routes

`withRouting()` mounts the layer's route files with Laravel's conventions. See [Routing](/layers/routing).

## Views, translations and components

`withViews()`, `withTranslations()` and `withComponents()` register the layer's resources under its package name: `view('orders::index')`, `__('orders::messages.placed')`, `<x-orders::alert />`. See [Views and components](/layers/views-and-components).

## Policies

Laravel discovers a policy that sits in the `Policies` namespace of its model's layer, the same way it does for `app/`:

| Model | Policy found |
|-------|--------------|
| `Functional\Orders\Models\Order` | `Functional\Orders\Policies\OrderPolicy` |
| `Functional\Users\Models\User` | `Functional\Users\Policies\UserPolicy` |

`osdd:policy OrderPolicy --model=Order --layer=functional/orders` creates the policy in that namespace. Register a policy that lives elsewhere by hand:

```php
use Illuminate\Support\Facades\Gate;

public function boot(): void
{
    Gate::policy(Order::class, OrderAccessPolicy::class);
}
```

## Commands, observers and events

Anything a Laravel service provider does works in a layer provider:

```php
public function boot(): void
{
    Order::observe(OrderObserver::class);

    Event::listen(OrderPlaced::class, SendOrderConfirmation::class);

    $this->commands([PruneAbandonedOrders::class]);
}
```

`osdd:command` adds the `commands()` call for you. With `osdd.events.discover` on, the listeners of the layer's `src/Listeners` are registered without `Event::listen()`: see [Events](/layers/events).

:::tip
Keep each layer's wiring in its own provider. A provider that registers classes of another layer hides a dependency that `composer.json` does not show.
:::
