title: Events
description: OSDD registers the listeners of every layer without Event::listen(), as Laravel does for app/Listeners.
---

Laravel discovers the listeners of `app/Listeners` on its own. It guesses each class name from the file path under the project root, so it skips the listeners of a layer. OSDD discovers them too, and this is on by default.

## Turning it off

To register every listener by hand instead, set `osdd.events.discover` to `false` in `technical/osdd/config/osdd.php`:

```php [technical/osdd/config/osdd.php]
'events' => [
    'discover' => false,
],
```

The value must be a real boolean: anything else throws when the application boots.

## What is discovered

Every class in a layer's `Listeners` folder, under its source directory (`src/Listeners` for a layer mapped to `src/`), sub-folders included. OSDD names each file through the layer's `autoload.psr-4`, then applies Laravel's own rules: each public `handle*()` or `__invoke()` method listens to the event class of its first parameter, union types included, and `ShouldBeDiscovered` is honoured.

```php [functional/billing/src/Listeners/SendInvoice.php]
<?php

namespace Functional\Billing\Listeners;

use Functional\Orders\Events\OrderPlaced;

class SendInvoice
{
    public function handle(OrderPlaced $event): void
    {
        // ...
    }
}
```

`OrderPlaced::dispatch($order)` now runs `SendInvoice::handle()`. Generate a listener in a layer with:

```bash
php artisan osdd:listener SendInvoice --event='\Functional\Orders\Events\OrderPlaced' --layer=functional/billing
```

`--event=OrderPlaced` names an event of the layer itself (`Functional\Billing\Events\OrderPlaced`); start the name with a backslash for an event of another layer.

A file that does not declare the class its path names is skipped.

:::note
`functional/billing` uses an event of `functional/orders` here: require `functional/orders` in `functional/billing/composer.json`, or [`osdd:check`](/commands/osdd-check) reports it.
:::

## Model events

A discovered listener whose `handle()` takes a model, such as `handle(Order $order)`, is registered for an event named after the model class, `Functional\Orders\Models\Order`. Nothing dispatches that event: Eloquent dispatches string events such as `eloquent.deleting: Functional\Orders\Models\Order`, so the listener never runs. Laravel does the same with `app/Listeners`.

To react to a model event, turn it into an event class with the model's `$dispatchesEvents`, and type the listener on that class:

```php [functional/orders/src/Models/Order.php]
protected $dispatchesEvents = [
    'deleting' => OrderDeleting::class,
];
```

```php [functional/billing/src/Listeners/CancelInvoice.php]
public function handle(OrderDeleting $event): void
{
    // ...
}
```

Or write an observer, and register it with `#[ObservedBy(OrderObserver::class)]` on the model or `Order::observe(OrderObserver::class)` in the layer provider's `boot()`:

```bash
php artisan osdd:observer OrderObserver --model=Order --layer=functional/orders
```

To keep a class that takes a model in `src/Listeners` without registering it, implement `Illuminate\Contracts\Events\ShouldBeDiscovered` and return `false` (Laravel 13.12 and later), or move the class outside `src/Listeners`:

```php
use Illuminate\Contracts\Events\ShouldBeDiscovered;

class SyncOrder implements ShouldBeDiscovered
{
    public static function shouldBeDiscovered(): bool
    {
        return false;
    }
}
```

## Listeners registered by hand

The discovered listeners are registered once the application has booted, after every provider's `boot()`. A listener already registered for the same event and the same method is skipped, so these run once:

```php
Event::listen(OrderPlaced::class, SendInvoice::class);
Event::listen(OrderPlaced::class, SendInvoice::class.'@handle');
Event::listen(OrderPlaced::class, [SendInvoice::class, 'handle']);
```

in a provider's `boot()`, or in the `$listen` array of an event service provider. A listener registered later, in a `booted()` callback or at runtime, is not seen and runs twice. So does a listener wrapped in a closure, such as `Event::listen(fn (OrderPlaced $event) => app(SendInvoice::class)->handle($event))`, which is not recognised. Do not register a listener of `src/Listeners` by hand, unless you need to [set its order](#making-an-order-explicit): discovery already does.

## Order

The listeners of an event run in this order:

1. The listeners registered while the providers boot: `Event::listen()` in a `boot()`, the `$listen` array of an event service provider, and the listeners Laravel discovers in `app/Listeners`.
2. The discovered layer listeners, by layer name, then class name, then method name, in byte order.

So the listeners of `functional/billing` run before those of `functional/orders`, and within a layer `Audit` runs before `SendInvoice`, `Billing\SendReceipt` before `Ledger`, and `handle` before `handleShipped`. The order is the same on every machine, and so is the list `event:cache` writes.

### Making an order explicit

The discovery order is stable, but it is not a design tool: renaming a class or adding a layer changes it. When two listeners must run one after the other, say so in the code:

- one listener that calls the steps in order;
- a follow-up event, dispatched by the first listener and listened to by the second;
- both listeners registered by hand, in order, in one provider's `boot()`. Discovery skips them, so each still runs once.

```php [functional/billing/src/Providers/BillingServiceProvider.php]
public function boot(): void
{
    Event::listen(OrderPlaced::class, ChargeCustomer::class);
    Event::listen(OrderPlaced::class, SendInvoice::class);
}
```

## In production

`php artisan event:cache`, which `php artisan optimize` runs, caches the layer listeners with the application's ones, so a request never scans the folders. They are stored under the `Lomkit\Osdd\Events\LayerEventServiceProvider` key of `bootstrap/cache/events.php`; OSDD registers that provider for you.

As with `app/Listeners`, a listener added after `event:cache` stays unregistered until `event:cache` runs again, and `event:clear` goes back to scanning. Check the result with:

```bash
php artisan event:list
```
